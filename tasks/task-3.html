Task 3: Hands-On with the IEEE-CIS Dataset

Load the data, explore it deeply, and build a baseline Isolation Forest.

Key Points

Dataset

Load the IEEE-CIS Fraud Detection dataset (train_transaction.csv and train_identity.csv, merged on TransactionID). Check the shape and the class imbalance in isFraud, and separate the raw columns (TransactionAmt, ProductCD, card type, etc.) from the anonymized V1-V339 features.

Implementation

Using scikit-learn's IsolationForest, fit a baseline model on the transaction features, with isFraud withheld during training. Leave contamination at its default for now, tuning comes later.

About the Data

The full dataset, rules, and file downloads are on Kaggle: IEEE-CIS Fraud Detection. It's provided by Vesta Corporation, a payment service company, from real-world e-commerce transactions.

train_transaction.csv

About 590,540 rows, one per transaction, joined to the identity file on TransactionID. Columns include TransactionDT (a time offset in seconds from an unspecified reference date, not a real timestamp), TransactionAmt (USD), ProductCD, card1-card6 (card type, category, issuing bank, country), addr1/addr2, P_emaildomain/R_emaildomain, C1-C14 (counting features, e.g. how many addresses are tied to the card), D1-D15 (time deltas, e.g. days since a previous transaction), M1-M9 (match flags, e.g. whether the name on the card matches the name on the address), and V1-V339 (Vesta's own engineered features). The target is isFraud, a binary label with roughly a 3.5% fraud rate. Vesta withholds the exact meaning of the C, D, M, and V columns for privacy reasons, so some of this is inherently a black box, you don't need to know what a column means to notice it behaves differently for fraud vs. not.

train_identity.csv

About 144,233 rows, far fewer than the transaction file, not every transaction has identity data attached, so the join is a left join and plenty of rows will have missing identity columns entirely. It holds network and device information collected by Vesta's fraud protection system: things like IP, ISP, and proxy signals, plus device and browser fingerprints (DeviceType, DeviceInfo). The id_01-id_38 columns are masked the same way as the transaction file's C/D/M columns; the numeric ones (roughly id_01-id_11) cover things like device rating, IP/proxy rating, and behavioral signals such as login attempts or time spent on a page.

Assignment 3, Part 1: Data Exploration

Start here, and spend real time on it before touching the model. Dig into the dataset and make graphs, whatever you find interesting is fair game, not just the obvious ones:

  • Class imbalance: how rare is fraud here, exactly? A bar chart of isFraud counts.
  • Distribution of TransactionAmt, overall and split by fraud vs. not. Try a log scale, the raw distribution is usually very skewed.
  • Categorical features like ProductCD and card type: do any categories have a noticeably higher fraud rate than others?
  • Missing values: which columns are mostly empty, and does missingness itself look different between fraud and non-fraud rows?
  • Anything in the anonymized V1-V339 features that stands out, even without knowing what they mean. A correlation heatmap of a subset, or a couple that separate fraud from non-fraud visually.

Write up what you found, in your own words: what surprised you, what confirmed what you expected, and what you'd want to dig into further.

Assignment 3, Part 2: Baseline Results Report (Stretch Goal)

This part is a stretch goal. Part 1 is the priority this week, focus your time there, and it's okay if you don't get to this. If you do have time left over, fit the baseline Isolation Forest and write a short report on what it actually did:

  • Plot the distribution of anomaly scores across all transactions.
  • Pull out the 10 most anomalous transactions. What do they look like compared to a typical transaction?
  • Peek at the withheld labels now: how many of your top anomalies are actually fraud? This is a sanity check, not tuning, don't go back and adjust the model to chase this number.
